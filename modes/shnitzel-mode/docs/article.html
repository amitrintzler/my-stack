Shnitzel mode

I built a watchdog for my own engineering work. Then I audited it and found it had been telling me to merge a build that was failing. Here is the whole thing, including the parts that broke.

There is no potato mode. The thing I went looking for is poteto mode, the entry command of a plugin called pstack, written by Lauren Tan, whose handle is poteto. It gets misheard constantly. I misheard it myself, spent an afternoon searching for a plugin that does not exist, and eventually found the real one.

The mishearing turned out to be useful. Because I arrived with no preconceptions, I read pstack as an artifact rather than as something to install, and what struck me was not any individual skill. It was the structure. A router that copies a playbook's steps verbatim into the todo list before the agent reasons about the task. Principles kept as separate files, loaded only when they apply. Four models spawned in parallel and made to argue before a design is accepted.

Those are context window design decisions dressed as documentation, and they are mostly right. What followed was a week of building an overlay on top, and the useful output is not the code. It is a handful of decisions that generalise, and three defects that only turned up because I went looking. The defects are the more interesting half, so they get their own section rather than a footnote.

The four layers

Start here, because almost every complaint about agent tooling turns out to be one layer being asked to do another layer's job.

The runtime supplies the hands: shell, files, git, the network, subagents where it has them, and MCP servers. Above it sits engineering craft, which is what pstack is: opinionated about how to think about code, deliberately silent about your organisation. Above that sit your constraints: your git rules, your clouds, your approval boundaries, your accumulated knowledge about your own repositories. And above all of it, you, deciding what is worth building at all.

Overlay, not fork

The first real decision was whether to copy pstack and edit it, or leave it installed and build alongside.

Forking is tempting because it is total. It is also a permanent tax. pstack is 47 skills, so every upstream release becomes a manual three-way merge across 47 files, forever, and the merge is prose rather than code, so no tool helps you. An overlay costs you the ability to rewrite what upstream wrote. In exchange, upstream updates itself and you own eight files instead of fifty-five.

The rule that keeps an overlay honest is that you have to actually delete. When upstream ships something covering ground you covered worse, remove yours. Refusing to delete is how an overlay quietly becomes a fork with extra steps.

Roles, not vendors

pstack names Anthropic model slugs inline. Correct for its author, wrong for anyone running several vendors.

The fix is small and worth stealing. No instruction file names a model. It names a role: the judgment model, the instruction-follower, the cheap one, and the review panel. Roles resolve through a single file the human fills in once per machine. A skill that hardcodes a slug is a defect, because the failure is invisible: everything works until you switch runtimes, and then it works worse for reasons nobody traces back.

A review panel that spans one vendor is a panel that agrees with itself. That is the same failure as a single-cloud architecture, and it deserves the same flag.

The line an agent does not cross

Every framework has an autonomy section. pstack's says proceed on reversible work and stop for force-push, deploys, data deletion and customer messages. Reasonable, and looser than most organisations can accept.

Mine is longer: no push, no merge, no pull request, no comment posted, no apply, no deploy, no deletion of data, no credential rotation, no access revocation, no message that leaves the machine, no commit to a protected branch, nothing installed on the host.

The important property is not the list. It is that no instruction inside a session widens it. "Run until done", "be fully autonomous", "I am going to bed" all widen the reversible set and none of them unlock the list. An autonomy override that can be granted by the text being processed is not an override.

Break 1, by design rather than by code

I wrote that list in terms of shell commands. No git push, no terraform apply. Then I noticed a connected GitHub MCP server can open a pull request without touching a shell at all. The stop list does not see it, nothing blocks it, and the report still says drafts only, because as far as the instructions are concerned it was.

Write the list in terms of effects, not commands. Then do not rely on it: scope the token. A read-only credential turns a paragraph of good intentions into something the platform enforces.

The deterministic half

This is the idea I would keep if I had to throw everything else away.

Much of what people ask agents to do daily is not judgment. It is gathering. Is CI green, what needs my review, has anyone commented, is anything stuck. Asking a model means it issues a dozen API calls, burns context on the responses, and produces a slightly different shape every time.

Split it. Gathering goes into plain shell scripts that make every query themselves and emit one compact JSON document. Judgment reads that document. The scripts contain no mutating command at all, which is why they are safe to run hourly with nobody watching, and they cost nothing because no model is attached until something is worth reading.

A simulation: three runs, one morning

The second half of making this survivable is dedupe. Every finding carries an identifier and a fingerprint, where the fingerprint is whatever should make it feel new again: the head commit for a pull request, the run SHA for a failed build, the thread count for review comments.

Here is what that actually looks like. This is real output from the test fixtures, not an illustration. First run, cold state:

Twenty-one findings across four collectors, ranked, first action per item.

Ten minutes later, nothing has changed. This is the run that decides whether the tool survives contact with a real week:

$ bin/digest.sh --pretty

shnitzel watch  2026-08-25T17:50:12Z
  new 0 of 9, 9 already seen

Two lines. No list. Silence is the correct output.

Now someone pushes a commit to pull request 41. The head SHA moves, so its fingerprint changes, so it becomes new again. Everything else stays suppressed:

$ bin/digest.sh --pretty

shnitzel watch  2026-08-25T18:12:44Z
  new 3 of 9, 6 already seen

  [2] my_pr_ci_red         acme/api
      PR #41 checks failing: Add retry to poller
  [2] my_pr_unanswered     acme/api
      PR #41 has 1 unresolved review threads
  [3] my_pr_conflict       acme/api
      PR #41 has conflicts

Exactly the three findings attached to the changed pull request. Not the other six.

Without that, an hourly check tells you the same six things sixty times a day and you stop reading it inside a week. With it, an empty report is genuinely information.

What broke

I set aside a session to attack my own work rather than extend it, using the harshest review standard I had. It found three real defects. All three were silent, which is the worst class for anything whose job is to tell you when something is wrong.

Break 2: it told me to merge a failing build

GitHub's statusCheckRollup returns two different node types in one array. A modern CheckRun carries a conclusion field. A legacy StatusContext, which is what you get when Jenkins or an older CI posts commit statuses, carries state and has no conclusion at all.

My filter read only conclusion. In any repository whose CI posts statuses rather than checks, every failing run was invisible.

That alone would be a bad miss. What makes it worse is what happened next. With zero failures seen, an approving review and no conflicts, the very same pull request matched the next rule down: approved, green, waiting only on your merge.

Break 3: a stall that never existed

Feature ledgers record a stage_since date. My age calculation appended a time to it, so a value already written as a full timestamp became unparseable, fell through a catch, and returned 9999 days. Any feature whose date was written with a time reported a permanent stall at severity 4, forever, and no amount of updating the ledger would clear it.

$ # the same field, written two ways
  2026-08-05           -> 22 days     correct
  2026-08-05T14:30:00Z -> 9999 days   permanent false stall

Fixed by normalising the value first. And a second change that matters more than the fix: a date that is genuinely unreadable now reports as feature_bad_date rather than as very old. Absence of data and a real finding should never look the same, and in the original they did.

Break 4: an empty fingerprint on one platform

The scope checker hashed its findings with md5sum, which does not exist on macOS. The fallback produced an empty string rather than an error, so every scope finding carried the same empty fingerprint, which the dedupe layer read as unchanged. On a Mac, each of those findings would have been reported exactly once and then suppressed permanently, including when the underlying leak got worse.

Fixed with a portable hash that falls through md5sum, then md5, then cksum, and verified on all three branches in isolation rather than assumed.

The pattern in all three

Every one of them failed by producing plausible output rather than an error. A missing field became zero failures. An unparseable date became a very old date. A missing binary became an empty hash. In each case the system carried on and said something reasonable.

The lesson I am taking forward is narrow and testable: absence of data must never be representable as a value. If a probe cannot answer, it has to say so, and the report has to distinguish "nothing is wrong" from "I could not look".

Why the fixtures did not catch them

Because I wrote the fixtures. Every mock returned the shape I expected, so every mock-shaped assumption was confirmed rather than tested. The first two defects only appeared when I went looking at the API documentation for shapes I had not handled, and the third only when I asked which of my dependencies do not exist on the platform I actually run.

That is a general result and not a flattering one. Self-authored fixtures verify that your code matches your beliefs. They say nothing about whether your beliefs match the system.

Knowledge has exactly one home

Once an agent writes things down and reads them back, you have built a memory, and memories leak. A constraint learned on one project turns up as an assumption on the next. It arrives phrased as knowledge, so nobody questions it. If your projects belong to different clients, this stops being a quality problem.

A checker then looks for the four ways this leaks. I want to be precise about what that buys, because the name oversells it. It is a smoke detector, not a firewall. It finds a lesson naming a foreign repository after it has been written. Real prevention comes from the filesystem: one project per worktree, so the other material is not on disk at all.

$ bin/scope-check.sh --pretty

  [3] scope_foreign_repo    lesson scoped to acme/api names acme/billing, acme/web
  [3] scope_mismatch        file declares global but sits at a path meaning repo:acme/web
  [3] scope_missing         lessons file has no scope header
  [3] scope_cross_feature   feature 007 references 008-audit-log
  [3] scope_foreign_draft   drafts in acme-api reference acme/web

All four leak classes, proven against deliberately planted fixtures.

Measure what you ignore

Any system that reports to a human decays the same way. It surfaces something you have decided not to care about, you skim past it, and within a month you skim past everything.

The usual fix is to ask whether the reports are useful, which produces polite and useless answers. The better fix is to measure. Record when each open finding was first seen, and log the mean age per category. Two categories in the fixture run came out like this:

46mean days open, stale pull requests, never actioned
30mean days open, security advisories, never actioned
30day threshold above which a category is proposed for demotion

A check you ignore is not a safety net. It is a habit of ignoring, and it generalises to the checks that matter.

Those two numbers drive a weekly proposal: here are the categories you have not acted on in a month, here is a config change, with the figure behind each line. It proposes and stops. Config that quietly tunes itself is config you can no longer reason about, and the first time it hides something real you will have no idea why.

What actually transfers

Strip away the implementation and five things are left that apply to any agent tooling, including tooling built on something other than what I used.

Separate gathering from judgment. Anything deterministic belongs in a script whose output a model reads. Highest leverage decision available, and it costs almost nothing.

Name roles, not vendors. One indirection file, and your instructions survive every model deprecation and every runtime switch.

Write the stop list in terms of effects. Then assume it will be circumvented and scope the credentials, so the important half is enforced somewhere other than in prose.

Give knowledge exactly one home, and make promotion cost evidence. Memory without scope is contamination with extra steps.

Make absence of data unrepresentable as a value. This is the one I learned the hard way, three times in one week. Zero failures, a very old date and an empty hash were all the system saying "I could not look" while sounding like it had looked.

None of that is about any particular framework, which is convenient, because the frameworks will keep changing. The mishearing was the best part of the exercise. I went looking for a potato and found a set of questions instead, and then found three bugs by taking the questions seriously.

Built as an overlay on pstack by Lauren Tan, ported to Claude Code by michael-denyer, both MIT. No pstack content is copied into it; the coupling is by skill name with a documented fallback for every reference.
