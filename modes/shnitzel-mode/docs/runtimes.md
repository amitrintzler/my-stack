# Runtime adapters

All support claims distinguish detected binaries, contract tests and live acceptance. See `docs/acceptance.md` for this revision's results. Installation alone is not proof that a skill affects behavior.

Claude Code uses the installed plugin or shared skills reached through its managed CLAUDE.md block. Native pstack hooks read the runtime's pstack-models.md. Shnitzel sets session hook off and supplies the only automatic routing mandate. Explicit poteto-mode still loads upstream in full. Honor CLAUDE_CONFIG_DIR and the plugin root exposed by the runtime rather than assuming one cache path.

Codex uses shared skills plus the managed AGENTS.md block under CODEX_HOME. Its current available tools, models and effort values are authoritative; a static table is not. Do not infer tool absence from an older port mapping. Use structured user input when the host exposes it. Required independent review stays required when delegation is unavailable. Goals and continuation budgets are not verified exact token caps.

Gemini CLI supports skills and may expose subagents and hooks. Detect its installed capabilities rather than assuming none exist. Use the Gemini pstack-models.md sheet. Headless JSON reports usage; turn limits do not enforce token caps. The verification toolchain can be installed in an isolated prefix without replacing the user's global commands.

Cursor runs original pstack natively: install Cursor's pstack plugin from its marketplace, the same upstream that the lock records as `original_version`, not the port. Shnitzel installs as a Cursor plugin (`.cursor-plugin/plugin.json`) carrying the skills, `shnitzel-agent` and one always-applied rule, `rules/shnitzel-mode.mdc`, which holds the same admission text as the other runtimes' managed block (a contract test keeps them identical). From a checkout, `./install.sh --apply cursor` links the plugin folder to `~/.cursor/plugins/local/shnitzel-mode`; Teams and Enterprise can import the repository, whose root `.cursor-plugin/marketplace.json` lists it. The installer writes no model sheet for Cursor: pstack's own setup-pstack owns `~/.cursor/rules/pstack-models.mdc`, and until it runs pstack uses its upstream default models rather than inheriting the session. Cursor's marketplace serves its current pstack, so it can drift from the lock between Shnitzel releases. Cursor also scans `~/.agents/skills` and `~/.claude/skills`; when another runtime's install put `shnitzel-mode` or the port's `poteto-mode` there, Cursor sees them beside the plugin's copies, and `bin/doctor.py` lists them. No hook and no MCP server ship for Cursor. Contract tests and Cursor's own plugin validator cover the manifests and installer; a live Cursor session has not been run.

Cowork uses the self-contained folder produced by bin/cowork-package.py under .runtime/cowork, starting with its START.md. The engine and Shnitzel skills are copied into it so host-home symlinks are not required. A CLI acceptance run is not Cowork acceptance. Verify the actual app with a connected folder. Without accessible usage, report tokens unknown and do not claim enforced caps.

Local acceptance uses Codex's local-provider path with LM Studio and an installed Qwen model. This is one concrete local host, not a claim that every Ollama, aider or opencode frontend has been tested. Detect its tools and context capacity. Token consumption and wall time still matter without an API bill. Output limits alone do not cap a whole task.
